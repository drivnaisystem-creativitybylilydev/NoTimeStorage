# Square Production Payment Integration — Debug Reference

**Project:** NoTime Storage (Next.js + Supabase + Square Web Payments SDK)

This document is a reference prompt for a Cursor agent working on Square payment integration in a new project. It documents real issues encountered during the NoTime Storage integration and how each was resolved.

---

## Agent Prompt (paste this into a new project's Cursor agent)

> You are helping debug and configure Square payment integration in a Next.js project using the Square Web Payments SDK on the frontend and the Square Node SDK (`square` npm package) on the backend (server actions). Below is a record of real issues we encountered in a production Next.js + Supabase + Square project and how we resolved each one. Use this as a reference when diagnosing payment errors.
>
> **Stack:** Next.js 14+ App Router, TypeScript, Supabase (auth + DB), Square Web Payments SDK (browser), `square` npm package (server), Vercel hosting.

## Environment Variable Architecture

The project uses a single flag to switch between sandbox and production. All Square files read this flag — never hardcode the environment.

```env
# .env.local (local dev — always sandbox)
SQUARE_ENV=sandbox
SQUARE_SANDBOX_ACCESS_TOKEN=EAAAl9...
SQUARE_SANDBOX_APPLICATION_ID=sandbox-sq0idb-...
SQUARE_SANDBOX_LOCATION_ID=LJCWXNED52KP4

# Production keys (stored in Vercel env vars only — never in .env.local)
SQUARE_ENV=production              # only set this in Vercel
SQUARE_ACCESS_TOKEN=EAAAl6...
SQUARE_APPLICATION_ID=sq0idp-...
SQUARE_LOCATION_ID=LYKH0VGXG3J8T
```

**Rule:** `.env.local` always has `SQUARE_ENV=sandbox`. Vercel Production environment has `SQUARE_ENV=production`. This way local dev can never accidentally charge real cards.

## `lib/square/client.ts` — the single source of truth

```ts
import { SquareClient, SquareEnvironment } from 'square';

const isSandbox = process.env.SQUARE_ENV !== 'production';

export const squareClient = new SquareClient({
  token: isSandbox
    ? process.env.SQUARE_SANDBOX_ACCESS_TOKEN
    : process.env.SQUARE_ACCESS_TOKEN,
  environment: isSandbox ? SquareEnvironment.Sandbox : SquareEnvironment.Production,
});

export const squareConfig = {
  isSandbox,
  applicationId: isSandbox
    ? process.env.SQUARE_SANDBOX_APPLICATION_ID
    : process.env.SQUARE_APPLICATION_ID,
  locationId: isSandbox
    ? process.env.SQUARE_SANDBOX_LOCATION_ID
    : process.env.SQUARE_LOCATION_ID,
};
```

The frontend reads `squareConfig.applicationId` and `squareConfig.locationId` via an API route (`/api/square-config`) so these never leak to the client bundle.

## Issues We Hit and How We Fixed Them

### Issue 1: "source not found" / INVALID_TOKEN error from Square API

**Symptom:** `chargeDeposit` or `chargeBookingPayment` returns `{ success: false, error: "source not found" }` or Square returns `INVALID_TOKEN`.

**Root cause:** The card nonce (sourceId) was generated by the **sandbox** Web Payments SDK but sent to the **production** Square API (or vice versa). The nonce is environment-specific — a sandbox nonce is rejected by production and vice versa.

**Fix:**
- Both the frontend SDK load URL and the backend Square client must use the same environment.
- Frontend: the SDK URL switches on `isSandbox`:
  ```ts
  const scriptSrc = isSandbox
    ? 'https://sandbox.web.squarecdn.com/v1/square.js'
    : 'https://web.squarecdn.com/v1/square.js';
  ```
- Backend: `squareClient` uses `SquareEnvironment.Sandbox` or `SquareEnvironment.Production` based on the same `SQUARE_ENV` flag.
- **Never mix** environments. One env var controls both.

---

### Issue 2: Double `SQUARE_ENV` declaration in `.env.local`

**Symptom:** Confusing behavior; one value was set twice (sandbox declared at top and bottom of file).

**Fix:** Remove the duplicate. Keep exactly one `SQUARE_ENV=sandbox` in `.env.local`. The second one was left in accidentally and Node reads only the first occurrence for some dotenv parsers (or the last — behavior is parser-dependent). Clean it up:

```env
SQUARE_ENV=sandbox  # exactly once
```

---

### Issue 3: Location ID inactive or not found in production

**Symptom:** Square API returns `LOCATION_NOT_FOUND` or payment fails with a location-related error after switching to production keys.

**Root cause:** The production Location ID was auto-generated when the Square app was created and may be inactive (not yet activated as a real business location).

**Fix:**
1. Go to developer.squareup.com → your app → Production → Locations.
2. Confirm the location shows as **Active**. If it's inactive, activate it from the Square Seller Dashboard (not the Developer Dashboard).
3. Copy the exact Location ID (e.g. `LYKH0VGXG3J8T`) and confirm it matches `SQUARE_LOCATION_ID` in your Vercel env vars.

---

### Issue 4: `BigInt` serialization error

**Symptom:** Runtime error like `TypeError: Do not know how to serialize a BigInt` when logging or returning payment objects.

**Root cause:** The Square SDK uses `BigInt` for `amountMoney.amount`. If you try to `JSON.stringify` or return the full `payment` object to the client, Node throws.

**Fix:** Only extract what you need from the response:
```ts
const { payment, errors } = await squareClient.payments.create({ ... });
// Only use payment.id (string) — never JSON.stringify the full payment object
return { success: true, paymentId: payment.id };
```

---

### Issue 5: Idempotency key reuse causing "idempotent_key_reused" errors

**Symptom:** Square returns an error about idempotency key reuse when a user retries payment.

**Root cause:** If you hardcode or reuse the same idempotency key across requests (e.g. a fixed UUID per booking), Square will reject the second attempt if the first succeeded (correct behavior) but also if the first failed for transient reasons.

**Fix:** Generate a fresh `randomUUID()` per charge attempt. Do not derive the idempotency key from the booking ID:
```ts
import { randomUUID } from 'crypto';

await squareClient.payments.create({
  sourceId,
  idempotencyKey: randomUUID(), // fresh per attempt
  ...
});
```

If you want idempotency per booking (so retrying the exact same booking doesn't double-charge), store the idempotency key in your DB when you first create it and reuse that stored key on retry.

---

### Issue 6: `deposit_paid` flag not updating after successful charge

**Symptom:** Charge succeeds (Square returns a payment ID) but the user is not redirected to booking because `users.deposit_paid` is still `false`.

**Root cause:** The Supabase update was done via the anon client, which was blocked by RLS. The user's JWT didn't have permission to update their own `users` row.

**Fix:** Always use `createAdminClient()` (service role) for writes in server actions. The admin client bypasses RLS and is safe to use in server-only code:
```ts
const supabase = createAdminClient(); // not createClient()
await supabase
  .from('users')
  .update({ deposit_paid: true })
  .or(`id.eq.${profile.id},auth_id.eq.${user.id}`);
```

---

### Issue 7: Web Payments SDK card instance not re-initialized after page navigation

**Symptom:** User goes back and forward between pages; the card input is blank or throws "Card already attached" / "payments instance not found."

**Root cause:** The Square `card.attach('#sq-card-booking')` was called multiple times on the same element because the `useEffect` ran on re-render.

**Fix:** Guard with a ref check before initializing:
```ts
if (cardInstanceRef.current) return; // already initialized
const card = await payments.card({ ... });
await card.attach('#sq-card-booking');
cardInstanceRef.current = card;
```
Also clear the container before attaching: `container.innerHTML = ''`.

## Pre-Launch Checklist: Sandbox → Production

Run through this before setting `SQUARE_ENV=production` in Vercel.

- [ ] Run a full end-to-end booking in sandbox: signup → deposit → configure → schedule → pay → confirmed. Watch terminal logs for `[chargeDeposit]` and `[chargeBookingPayment]` — both should log success.
- [ ] Confirm `SQUARE_LOCATION_ID` (production) is **Active** in Square Developer Dashboard → Production → Locations.
- [ ] Confirm production `SQUARE_APPLICATION_ID` and `SQUARE_ACCESS_TOKEN` are set in Vercel (not in `.env.local`).
- [ ] Set `SQUARE_ENV=production` only in Vercel → Production environment. Do NOT set it in Preview or local.
- [ ] Deploy to Vercel production. Do a real $1 test charge with a real card. Immediately refund from Square Dashboard (Payments → find charge → Issue Refund).
- [ ] Confirm refund goes through cleanly (Square sandbox refunds are instant; production refunds can take 2–7 days to appear on card statement but are processed immediately on Square's end).
- [ ] Confirm post-charge Supabase writes succeeded: check `users.deposit_paid = true` and `payments` table has a row for the test booking.
- [ ] Confirm confirmation emails (Resend) fired — check Resend dashboard → Logs.
- [ ] Keep `SQUARE_ENV=sandbox` in `.env.local` forever. Local dev should never touch production.

## Architecture Summary (for agent context)

| Layer | File | What it does |
|-------|------|-------------|
| **Env flag** | `.env.local` / Vercel | `SQUARE_ENV=sandbox\|production` switches everything |
| **Backend client** | `lib/square/client.ts` | Single `SquareClient` instance; reads env flag |
| **Deposit charge** | `lib/square/deposit.ts` | Charges $50, sets `users.deposit_paid = true` |
| **Storage charge** | `lib/square/charge-booking.ts` | Charges `booking.total_price`, sets `payment_status = 'paid'` |
| **Upgrade charge** | `lib/square/charge-upgrade.ts` | Charges delta for booking edits on paid bookings |
| **Frontend SDK** | `app/deposit/DepositForm.tsx`, `app/booking/payment/page.tsx` | Loads sandbox or production `square.js` based on `isSandbox` from `/api/square-config` |
| **Config API** | `app/api/square-config/route.ts` | Exposes `applicationId`, `locationId`, `isSandbox` to the client safely |
| **Auth guard** | All server actions | `createClient()` for auth check; `createAdminClient()` for all DB writes |
